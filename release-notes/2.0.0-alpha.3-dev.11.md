# 2.0.0 Alpha 3 Dev 11

Private vNext test line. Not published.

## OTA and build-transition handling

- Detects a platform tuple change across device, Android release, build ID, incremental build and fingerprint.
- Runs the transition guard from `post-fs-data.sh`, before this module's system overlay is mounted.
- Quarantines only the three controlled Thermal overlay files belonging to this module.
- Invalidates only the current device/build stock cache and preserves other build caches as diagnostic evidence.
- Recaptures the current build's stock Thermal files and regenerates the selected Polling and Outdoor profile.
- Publishes the regenerated overlay only after the existing transactional structural, manifest and exact-delta validators pass.
- Unsupported device/Android platforms and failed materializations remain stock-only with Thermal disabled.
- A failed tuple is not retried on every boot; a deliberate reinstall or Action transaction can retry it.

## Bootguard v3

- Evaluates an uncleared previous attempt before any current-boot rematerialization or mount.
- Arms the attempt only after the final current-build state has been selected and validated.
- Treats a pending OTA/platform transition as a one-attempt boundary; normal builds retain a minimum threshold of two and Canary diagnostic mode retains one.
- Clears the pending attempt only after Android reports boot completion, compatibility is safe, an expected active overlay matches the runtime files and the Thermal service answers two probes.
- Preserves pending state when runtime verification is incomplete, so the next boot can fail closed.
- Records build, module, transition, profile and overlay hashes for the last attempt and last verified-good boot.

## Terminology and observability

- Replaces obsolete exact-build activation labels with `PLATFORM_SUPPORTED`, `BUILD_EVIDENCE` and `dynamic_local_validation`.
- Exposes transition pending/phase/reason in compatibility and Action status records.
- Exact build IDs remain evidence labels only; supported Pixel 10 devices on Android 17 still rely on local stock-derived validation.

## Safety boundary

- No old-build Thermal overlay is restored after an OTA. The safe rollback is stock-only/skip-mount or module disable, because old vendor Thermal data is not assumed compatible with the new system build.
- Public Dev 10 remains the rollback package.
- Real OTA/reboot verification is still required before Dev 11 is considered release-ready.
- Mustang is the first planned OTA transition proof; Blazer, Frankel, Rango and non-Magisk root implementations remain additional coverage targets.
