# 2.0.0 Alpha 3 Dev 12

Private vNext test line. Not published.

## Source and integration

- Ports the ZRAM performance work proposed on `v2-perf` into the current Dev.11 OTA-rematerialization and Bootguard-v3 base.
- Keeps the imported Action and install-menu choices independent of pTune; pTune does not need to be installed or enabled.
- Preserves existing lz77eh hardware-accelerated ZRAM compression and the 100% ZRAM layout.

## ZRAM enhancements

- Adds configurable `vm.swappiness` with a validated range of 0 through 200 and a default of 100.
- Adds optional Transparent Huge Page policy values (`stock`, `always`, `madvise`, `never`); the default is `stock`, so Dev.12 does not silently change the platform THP policy.
- Keeps ZRAM maintenance/writeback delay controls and the lz77eh compression algorithm from the existing module path.

## Emerald Hill performance mode

- The menu wording inherited from `v2-perf` calls this an OC option. Technically, Dev.12 never requests a clock above the kernel-exposed maximum operating point.
- The optional mode pins the Emerald Hill devfreq user minimum to an admitted kernel frequency, normally the current `max_freq`.
- This is a maximum-frequency lock, not an unsupported-frequency CPU overclock. It can still increase power use, temperature and time spent at the highest accelerator frequency.
- Fresh and legacy-ambiguous configurations default to adaptive devfreq (`ZRAM_EMERALD_OC=0`).
- Activation requires all of: ZRAM enabled, the dedicated max-lock menu choice saved, the existing explicit ZRAM acknowledgement, a matching writable Emerald Hill devfreq node, and successful write/readback verification.
- Numeric `ZRAM_EH_TARGET_FREQ` values are accepted only when they do not exceed `max_freq` and, when exposed, occur in `available_frequencies`.
- The original `min_freq` is recorded and restored when the option is disabled or an apply fails.

## Boot and failure safety

- Standard ZRAM properties may be prepared in early service execution.
- The optional max-frequency lock is deferred until Android boot completion and Bootguard-v3 `success-verify` pass.
- No permanent 60-second wakeup loop is installed.
- Missing nodes, invalid targets or failed verification fall back to adaptive lz77eh ZRAM and do not become a boot prerequisite.
- Dev.11 OTA tuple quarantine, current-build Thermal rematerialization and Bootguard-v3 behavior remain authoritative.

## Validation status

- Repository regression coverage uses a fake writable devfreq node to verify apply, readback, baseline storage and restore.
- Static guards verify default-off behavior, absence of the unbounded service watcher and post-Bootguard activation ordering.
- Real Pixel 10 validation is still required for node naming, observed frequency, power/thermal behavior, ZRAM compression throughput and one-day app-retention behavior.

## Rollback

- Select standard ZRAM/no OC in the install or Action menu and reboot.
- Disable ZRAM and reboot to remove the 100% ZRAM layout.
- Disable/remove the module and reboot for full module rollback.
