# 2.0.0

2.0.0 promotes the device-tested Dynamic V2 line to the next stable release. This release candidate must complete repository CI and exact-package device verification before the tag, public asset, stable update metadata, README, and changelog are published.

## Dynamic thermal architecture

- Build guarded overlays from the device's own stock thermal configuration.
- Admit supported Pixel 10 codenames on Android 17 and validate monthly or Canary builds locally instead of requiring a static package for every build ID.
- Limit changes to the controlled Polling and Outdoor targets in the three managed thermal files.
- Fail closed to stock behavior when source structure, controlled deltas, manifests, active mounts, or runtime evidence do not validate.
- Quarantine stale overlays and rematerialize them after firmware or platform transitions.

## Thermal controls

- Polling Mode can retain stock values or change admitted `PollingDelay` values from `300000` to `5000`.
- Thermal profiles provide Stock, Outdoor Safe, Outdoor Plus, and Outdoor Extended choices.
- The Action Thermal Profile menu now includes the missing five-choice menu implementation, so selecting a profile applies the chosen route instead of returning to Settings.

## Memory controls

- Optional ZRAM sizing at approximately 100% of physical RAM with `lz77eh` where supported and `vm.swappiness=100`.
- Adaptive Emerald Hill operation for normal use plus a separate acknowledged experimental maximum-frequency minimum lock.
- Optional LMKD 1% swap-free policy with Magisk `resetprop` first, readback verification, `resetprop-rs` fallback, targeted reload, and bounded evidence.
- Independent pTune conflict detection and explicit high-risk coexistence override.

## Boot and recovery

- Bootguard tracks pending and last-good state, evaluates the previous boot, and can disable or skip the overlay after bounded failures.
- First install, module update, firmware/configuration changes, pending transitions, debug mode, or invalid evidence trigger full compatibility verification.
- Unchanged verified normal boots use the lightweight path while retaining automatic escalation when signed state changes.
- Magisk P/T/Z/L badges refresh after boot and Action changes without a permanent watcher.
- Module removal cleans both the Magisk module path and persistent module state.

## Repository verification gate

The release candidate must pass:

1. Shell syntax checks for release tooling, installer/runtime scripts, Action, Bootguard, Thermal, ZRAM, Emerald Hill, and LMKD paths.
2. Dynamic build admission, canonical validation state, Outdoor delta, Canary Safe-only, Action transaction, ZRAM/Emerald Hill, LMKD, menu-route, runtime evidence, Bootguard, pTune, release-note layout, and package-exclusion tests.
3. Exact package build and `dev_tools/verify-release-module.sh` verification.
4. Package limits: no excluded development content, at most 60 entries, at most 450000 bytes, `action.sh` at most 12000 bytes, and one installer menu process.
5. SHA-256 verification of the exact local candidate ZIP from the bound build metadata, without a separate hash sidecar.

## Required device verification before public release

Install the exact CI artifact without rebuilding it, then verify:

1. Dirty-flash/update installation completes and the final installer summary is correct.
2. First boot reports `boot_verification_mode=full` and all expected P/T/Z/L badges return.
3. A later unchanged boot with Debug Logging set to Silent reports `boot_verification_mode=fast`.
4. Action → Settings → Thermal Profile can select Stock, Outdoor Safe, Outdoor Plus, and Outdoor Extended; each selection persists and reports the expected active profile.
5. Thermal active-overlay and controlled-delta evidence pass for the selected profile.
6. ZRAM reports active swap, non-zero disksize, expected algorithm where available, and `vm.swappiness=100` when enabled.
7. LMKD Reload Evidence reports property readback, writer, reload method, service state, and success when the experimental option is enabled.
8. Reboot and removal/recovery paths remain healthy.

## Publication rule

Do not merge, tag, publish a public asset, or change `update.json` until the exact candidate artifact and its device evidence pass. The public 2.0.0 release must reuse the verified package bytes and SHA-256 unchanged.
