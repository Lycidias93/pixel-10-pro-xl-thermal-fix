# Pixel Thermal & Memory Control 2.1.0-alpha.2

This is the second **vNext device-expansion prerelease**. Stable users should remain on 2.0.1 unless they are intentionally testing Pixel 9-series / Pixel 10a support.

## Alpha.2 hardening

- **pTune coexistence is now blocked on experimental Pixel 9 / Pixel 10a targets.** The installer no longer offers the pTune override on those devices, remembered override state is forced off, and the lower-level guard independently refuses an override if pTune is active or staged.
- Adds a compact read-only **vNext readiness state** in `guard/support-readiness.env`. It is written after install and refreshed after boot so support packages can distinguish local materialization from real post-reboot active-overlay verification.
- Adds explicit readiness states including `install_ready_reboot_pending`, `runtime_verified`, `safe_nonactive_state`, and `needs_attention`, together with layout, polling, compatibility and next-action fields.
- Adds a maintained device evidence matrix that separates `platform_admitted`, `layout_evidenced`, and `runtime_verified` instead of treating device admission as verification.

## Experimental Pixel 9 / Pixel 10a policy

The conservative alpha.1 policy remains unchanged:

- Pixel 9 (`tokay`), Pixel 9 Pro (`caiman`), Pixel 9 Pro XL (`komodo`), Pixel 9 Pro Fold (`comet`), Pixel 9a (`tegu`) and Pixel 10a (`stallion`) are Android 17 experimental targets.
- Outdoor remains capped at **Stock / Outdoor Safe +1 C**. Alpha.2 does not unlock +2 C or +3 C from install-time validation alone.
- Full Bootguard verification remains mandatory for experimental targets.
- Firmware/platform transitions still remove stale experimental Thermal materialization and require reinstall before Thermal is re-enabled.
- Unsupported or ambiguous local stock layouts fail closed; ZRAM remains independent.
- pTune Thermal coexistence override is unavailable on these experimental devices.

## Evidence status

### Pixel 10a / stallion

Allen Chang's Android 17 `ZP11.260717.006` support snapshot established the `base + charge + lpm` controlled layout:

- `thermal_info_config.json`
- `thermal_info_config_charge.json`
- `thermal_info_config_lpm.json`

The selected stock files contained 37 `PollingDelay=300000` entries in total: 23 + 11 + 3. This remains **layout evidence**, not a claim of post-reboot Thermal runtime verification. Alpha.2 is intended to collect that missing install/reboot/runtime proof.

### Pixel 9 series

All five Pixel 9-series codenames remain `platform_admitted` for local stock validation. No Pixel 9-series device is marked exact-verified or runtime-verified in alpha.2 yet.

### Pixel 10 regression baseline

Pixel 10 flagships retain the `base + charge + throttling` layout and the existing Dynamic V2 safety model. The Pixel 10 Pro XL / `mustang` August Stable `CP2A.260805.005` AIO runtime regression remains a vNext baseline. That run used the `2.0.1-hotfix.1` candidate, so it is runtime-regression evidence rather than byte-identical proof of the public 2.0.1 ZIP.

## Included alpha.1 foundation

Alpha.2 keeps the alpha.1 device-expansion work:

- layout-aware three-file Thermal detection instead of a hard-coded third filename,
- local stock source caching and manifests,
- atomic overlay materialization,
- independent Outdoor delta validation,
- active-runtime verification,
- optional read-only installer Support Snapshot using the embedded v5 collector,
- support/runtime collector modes with ZIP, 7z-backed ZIP, then tar.gz packaging fallback.

## Test reporting

For Pixel 9-series and Pixel 10a tests, please provide:

1. device codename and Android build,
2. root implementation,
3. installer result,
4. Support Snapshot archive,
5. `guard/support-readiness.env` if available,
6. after reboot: P/T/Z/L status and whether the device booted normally,
7. runtime debug package if readiness does not become `runtime_verified`.

Device matrix: [`docs/vnext-device-test-matrix.md`](../docs/vnext-device-test-matrix.md)

Do not manually remove the +1 C cap or bypass the experimental pTune block. Both are intentional prerelease safety boundaries.
