# Pixel Thermal & Memory Control 2.1.0-alpha.2

This is the second **vNext device-expansion prerelease**. Stable users should remain on 2.0.1 unless they are intentionally testing Pixel 9-series / Pixel 10a support.

## Important changes

- **Pixel 10a / stallion has its first public alpha.2 field pass.** Allen Chang reports `2.1.0-alpha.2` working on an August Canary build with **WildKSU + HybridMount**, with installation completing without issues. This is strong tester evidence, but it is not promoted to the strict `runtime_verified` state yet because no Support Snapshot / post-boot readiness package accompanied the report.
- **pTune coexistence is blocked on experimental Pixel 9 / Pixel 10a targets.** The installer hides the override, remembered override state is forced off, and the lower-level guard independently refuses it.
- **vNext readiness is now explicit.** `guard/support-readiness.env` is written after install and refreshed after boot, with states such as `install_ready_reboot_pending`, `runtime_verified`, `safe_nonactive_state`, and `needs_attention`.
- **Experimental Thermal limits remain conservative.** Pixel 9-series and Pixel 10a stay capped at Stock / Outdoor Safe +1 C; alpha.2 does not unlock +2 C or +3 C from install-time validation or a tester report alone.
- **Evidence levels stay separate.** `platform_admitted`, `layout_evidenced`, and `runtime_verified` are tracked independently so device admission or a successful install is not mistaken for complete active-overlay verification.

## Experimental Pixel 9 / Pixel 10a policy

Pixel 9 (`tokay`), Pixel 9 Pro (`caiman`), Pixel 9 Pro XL (`komodo`), Pixel 9 Pro Fold (`comet`), Pixel 9a (`tegu`) and Pixel 10a (`stallion`) are Android 17 experimental targets. Full Bootguard verification remains mandatory. Firmware/platform transitions remove stale experimental Thermal materialization and require reinstall before Thermal is re-enabled. Unsupported or ambiguous local stock layouts fail closed, ZRAM remains independent, and the pTune Thermal coexistence override is unavailable on these devices.

## Pixel 10a evidence

Allen Chang's earlier Android 17 `ZP11.260717.006` support snapshot established the Pixel 10a `base + charge + lpm` layout using `thermal_info_config.json`, `thermal_info_config_charge.json`, and `thermal_info_config_lpm.json`. Those selected stock files contained 37 `PollingDelay=300000` entries in total: 23 + 11 + 3.

After the public alpha.2 release, Allen reported that `2.1.0-alpha.2` is working on `stallion` August Canary with WildKSU and HybridMount, and that installation completed without issues. He did not capture the install screen. No Support Snapshot archive, `guard/support-readiness.env`, P/T/Z/L state, runtime debug package, or exact Canary build identifier accompanied that report, so the strict matrix state remains `layout_evidenced` plus a tester-reported alpha.2 pass rather than `runtime_verified`.

## Pixel 9 series evidence

All five Pixel 9-series codenames remain `platform_admitted` for local stock validation. No Pixel 9-series device is exact-verified or runtime-verified in alpha.2 yet.

## Pixel 10 regression baseline

Pixel 10 flagships retain the `base + charge + throttling` layout and the existing Dynamic V2 safety model. The Pixel 10 Pro XL / `mustang` August Stable `CP2A.260805.005` AIO runtime regression remains a vNext baseline. That run used the `2.0.1-hotfix.1` candidate, so it is runtime-regression evidence rather than byte-identical proof of the public 2.0.1 ZIP.

## Included alpha.1 foundation

Alpha.2 keeps the alpha.1 device-expansion foundation: layout-aware three-file Thermal detection instead of a hard-coded third filename; local stock source caching and manifests; atomic overlay materialization; independent Outdoor delta validation; active-runtime verification; optional read-only installer Support Snapshot using the embedded v5 collector; and support/runtime collector packaging with ZIP, 7z-backed ZIP, then tar.gz fallback.

## Test reporting

For Pixel 9-series and Pixel 10a tests, please provide the device codename and Android build, root implementation, installer result, Support Snapshot archive, `guard/support-readiness.env` if available, post-reboot P/T/Z/L status and normal-boot result, plus a runtime debug package if readiness does not become `runtime_verified`.

Device matrix: [`docs/vnext-device-test-matrix.md`](../docs/vnext-device-test-matrix.md)

Do not manually remove the +1 C cap or bypass the experimental pTune block. Both are intentional prerelease safety boundaries.
