# Pixel Thermal & Memory Control 2.1.0-alpha.3

This prerelease continues the single **vNext 2.1 device-expansion line**. All supported Pixel 10, Pixel 10a and Pixel 9-series targets are carried by the same module and the same branch; there is no separate Pixel 9/10a feature branch.

Stable users should remain on the current stable release unless they intentionally want to test vNext device expansion or the revised ZRAM/Memory Killer controls.

## Main changes

- **ZRAM Action enable/disable is config-first and reboot-safe.** Action saves the requested state even when the mounted active module tree cannot be rematerialized immediately; `post-fs-data` remains authoritative for the actual pre-mount ZRAM layout.
- **Disabling ZRAM immediately clears the experimental Memory Killer selection.** Re-enabling ZRAM explicitly asks whether LMKD should remain stock or use the experimental 1% reload policy.
- **The real Magisk Action regression is fixed.** The previous `ZRAM layout removal failed` / `Existing configuration kept` failure no longer blocks the user choice.
- **Support Snapshot and status handling remain part of the device gate.** The repository-owned verifier covers `baseline`, `post-disable` and `post-reenable` phases and continues evidence collection across non-safety failures.
- **Pixel 9-series and Pixel 10a stay in the same vNext line.** Their conservative experimental policy remains unchanged: Android 17, full verification, Stock / Outdoor Safe +1 C maximum, pTune coexistence blocked, and local stock-layout validation required.

## Exact alpha.3 Pixel 10 Pro XL device gate

The alpha.3 runtime package content was verified on Pixel 10 Pro XL / `mustang`, Android 17 build `CP2A.260805.005`.

The complete sequence passed:

1. exact-candidate baseline verification;
2. real Magisk Action → ZRAM Disable without the historical abort strings;
3. reboot and `post-disable` verification with module ZRAM layout absent, stock ZRAM active and Memory Killer off;
4. real Action re-enable to ZRAM 100% adaptive + experimental LMKD 1%;
5. reboot and `post-reenable` verification;
6. Support Snapshot success.

Final `post-reenable` evidence included ZRAM 100% active at `16331833344` bytes, `lz77eh`, same-boot LMKD reload success, `ro.lmk.swap_free_low_percentage=1`, running `lmkd`, `failure_count=0`, `warning_count=0`, and complete Support Snapshot collection.

The clean alpha.3 CI intentionally rebuilds with the device-tested source epoch and requires the release ZIP SHA-256 to equal the already device-verified package hash:

`31a3679ba90fc1ea6b4d2267e5ef9b2dfed9c725399a7744bc7b56df04ac8583`

If byte identity is not reproduced, CI fails and publication is blocked.

## Pixel 10a evidence

Pixel 10a / `stallion` retains the alpha.2 evidence level: a real support snapshot established the `base + charge + lpm` Thermal layout, and a tester reported public alpha.2 working on an August Canary build with WildKSU + HybridMount. The strict matrix is not promoted to `runtime_verified` without the complete post-boot evidence package.

## Pixel 9-series evidence

Pixel 9 (`tokay`), Pixel 9 Pro (`caiman`), Pixel 9 Pro XL (`komodo`), Pixel 9 Pro Fold (`comet`) and Pixel 9a (`tegu`) remain admitted experimental Android 17 targets. Local stock-layout validation is mandatory and unsupported/ambiguous layouts fail closed. Their Outdoor cap remains +1 C until device-specific runtime evidence supports a later policy change.

## Safety boundaries

- Experimental Pixel 9 / Pixel 10a targets force full verification and block the pTune Thermal coexistence override.
- ZRAM remains independently reversible.
- LMKD 1% remains explicit and experimental; it is automatically cleared when ZRAM is disabled.
- Unknown or unsupported platforms do not receive the Thermal overlay.
- Existing emergency/shutdown thermal protections are not intentionally modified.
